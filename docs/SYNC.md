# 多设备同步（0.5.0）

手机、平板、电脑之间同步记录。三句话概括：

- **数据在本地**。每台设备各有自己的库，服务器不放业务数据 —— 这条约定没有变。
- **能直连就直连**。同一网段走局域网；跨网段先用云服务器换地址、直接打洞；只有打洞被
  对称 NAT 之类挡住时，才借服务器中转。
- **三路上都是密文**。配对时两端各自用一次性同步码推出组密钥，之后所有帧都是
  ChaCha20-Poly1305 加密的；服务器只转发字节，看不到内容。

---

## 一、同步什么

白名单登记制：`src-tauri/src/modules/sync/tables.rs` 里登记过的表才同步，没登记的
连捕获钩子都不会碰它。当前覆盖记录类全部（饮食 / 训练与组数 / 身体指标 / 待办 /
计划 / 课程 / 账本 / 番茄钟 / 自建食物与动作 / AI 会话与用量 / 语音纪要 / 知识库文件），
其中三类有刻意的例外：

| 例外 | 为什么 |
| --- | --- |
| 教务账号（密码、Cookie） | 凭证。同步它等于把学校账号复制到每台设备上，不做 |
| 模型 `api_key` | 同上。模型行同步（名字、单价、参数），密钥各设备各填一次 |
| 知识库索引（文档 / 分块 / 向量） | 派生物，各设备本地重建比传它便宜得多 |

大于 64KB 的文本列、以及聊天图 / 待办附件 / 语音 wav / 知识库媒体，都会**自动走 blob
通道**：对象里只留 `{__blob: <sha256>}` 引用，字节按内容寻址单独传、去重、可断点续传。
语音 wav 落到 `voice_sessions/<id>.wav`，会话媒体落到 `workspace/media/`，前端读到的
语义与同步前完全一致。

## 二、怎么判断谁改得新

**按对象（不是按表、更不是按档案）最后写入时间取胜**，时间相同时按设备号比大小：

- 每个对象有稳定的 uuid（自增主键只在本地有效），`sync_map` 维护本地 id ↔ uuid。
- 业务唯一键会**并表**：两台设备各自记了同一天的体重、各自建了同名的自建食物，
  同步后是一条（不是两条撞 UNIQUE）——`tables.rs` 的 `natural` 字段声明这些键。
- 输的那一版不丢：进 `sync_conflicts` 留档（含双方 hlc 与内容），设置页可查。
- 删除是**墓碑**（`deleted=1`），不是静默消失；墓碑一样参与 LWW。

冲突策略是 LWW 而不是逐字段合并：记录类数据里同一条被两端同时改不同字段的概率很低，
换来的是「任何两台设备、任意顺序同步，最终必然收敛」这个容易验证的性质。真要逐字段
合并，该做的是把对象拆成字段级 CRDT，那是另一个量级的工作。

## 三、三条路（`transport/`）

```
同一网段 ──广播找人（UDP 48991）──────────────► 局域网直连
    │
    └─ 跨网段 ──向云服务器要双方公网映射────────► 打洞直连
                    （UDP 48990）                    │
                                                     └─ 打不通 ──► 云端中继
                                                                  （HTTP 长轮询）
```

- **谁拨号**：设备号小的那台。两端的结论必然一致，不需要任何额外的「谁先连」协商。
- **局域网**：向 `255.255.255.255:48991` 广播自己的房间与端口，房间号对不上就不理。
  首次使用 Windows 会弹一次防火墙授权；拒绝也不影响，会自动落到中继。
- **打洞**：向服务器的 `UDP 48990` 周期发 `hello`，服务端把**它看到的**公网 ip:port
  告诉同房间的两台设备，两端同时向对方连发 PING 把 NAT 捅开。需要在阿里云安全组
  放行 UDP 48990。
- **中继**：服务器的**内存**邮箱（环形缓冲，10 分钟没人碰就消失，掉电即丢）。
  房间号本身就是凭证（128 位随机，配对时两端交换），所以别人猜不到、也无法拿它当
  免费网盘；另加每 IP 限流与房间数上限。
- **UDP 的可靠性是停等的**：一帧拆成 ≤1100 字节的数据报，等 ACK，超时重发（同 seq
  去重）。局域网 RTT 亚毫秒、跨网段常 <50ms，配合 128KB 分片足够；换来的是没有窗口 /
  乱序重排 / 拥塞控制这一整套。真要更快，该换 QUIC，而不是手写窗口。

## 四、一次同步谈些什么

明文 HELLO（HMAC 证明持有组密钥）+ **公钥钉死**（与配对时记下的不一致就拒连），
之后全部加密。阶段固定，两端的顺序由「谁拨号」决定，不会同时开口：

```
拨号侧：清单 ──► 收到索取 ──► 发对象（分块）──► 收到 blob 索取 ──► 发 blob ──► 等完成
被动侧：       ◄── 清单 ──► 索取 ◄── 对象 ──► 索取 blob ◄── blob ──► 完成
```

- 清单只带元信息（uuid / 表 / hlc / 设备 / 是否墓碑 / 大小），收方按本地已有的版本
  就能说「这条我不要」—— 增量同步的省流都在这儿。
- 引用（外键）解不开时**不塞 null**：这一条留到下一轮再试，游标为此回退重发。
- 阶段终止必须等回执。不等的话那条 ACK 会漏进下一个阶段，两边一起卡死（踩过）。
- 调试：`REIN_SYNC_DEBUG=1` 打印带线程号的报文序列。

## 五、存量与表结构

- **存量补录**：升级上来时库里已经有的行从来没进过捕获队列。首次运行会按表算
  「列名 + 类型」指纹，不一致就走一遍该表的存量行 —— 因此第一次同步会把历史数据
  一起带过去，之后只在结构变了时重跑。
- **结构演进**：对端版本更新、对象里有本机还没有的列 → 跳过那一列并计数，其余照常
  落地；对象里的未知列会原样转发给下一台。中间设备的版本落后不会卡住整条链路。
- **不回声**：应用远端对象会写库，写库又触发捕获钩子 —— 所以捕获那一步比对内容，
  与已存对象一样就不新增版本、不写日志。少了这条，两台设备会把对方的对象原样发回去，
  永远不收敛。

## 六、涉及的表与键

| 表 | 作用 |
| --- | --- |
| `sync_meta` | 本机身份与组：`device_id` / `device_name` / X25519 密钥对 / `group_id` / `group_secret` / 最近一次结果 |
| `sync_objects` | 每个对象的最新版本（uuid / 表 / hlc / 设备 / 墓碑 / 内容） |
| `sync_map` | 本地 id ↔ uuid |
| `sync_log` | 复制日志（本地改动与「应用来的远端改动」都追加）：对端游标 = 已确认的 seq |
| `sync_peers` | 已配对设备（公钥、上次走的哪条路、游标） |
| `sync_conflicts` | LWW 落败的那一版，供人回看 |
| `sync_blobs` | blob 目录（内容寻址；字节在 `sync_blobs/<前两位>/<hash>`） |

## 七、服务器新增的四个接口

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| POST | `/api/v1/sync/pair` | 开一个 5 分钟有效的人念短码 |
| POST | `/api/v1/sync/pair/<code>` | 另一台报码：互换公钥与房间号 |
| GET | `/api/v1/sync/pair/<code>` | 开码侧轮询「谁认领了」，用过即废 |
| POST/GET | `/api/v1/sync/relay/<room>` | 中继投递 / 长轮询取件（仅内存） |
| UDP | `:48990` | `hello` → 回「你被看到的公网 ip:port」+ 同房间对端映射 |
