Rein · ProgramPage 设计发散

健康方案页 · 10 个界面设计方案

现有 ProgramPage.vue 是一条直线流程：生成三档 → 选一档启用 → 看今日安排 + 本周列表 → 调参/复盘/归档。 它把「方案」当成一个静态配置对象来展示，而方案真正的价值是一段有节奏的时间旅程—— 用户需要知道「我选的这个到底多累」「我现在走到哪了」「我做得怎么样」「下一步该怎么办」。 下面 10 个设计围绕这四个缺口展开，全部基于现有 programEngine / programReport / weightTrend 已能算出的数据，不虚构字段。

01 · 决策期

三档参数对比矩阵

把「纵向三张卡」换成「横向一张表」，让选择变成对比而不是阅读。

现状痛点

现在是三张纵向堆叠的卡，每张 4 个数字。要比较「进取档比均衡档多练几天」，用户得上下滚动并在脑子里记住上一张卡的数字——三档方案的核心价值「差异」被埋掉了。

关键交互

  • 点列选中：整列高亮（accent 底），不用现在的圆点单选；视觉重心直接落在「你要的那套」。
  • 差异行强化：月度预期变化那行单独加重，因为这是用户唯一真正关心的结果指标，其余都是手段。
  • 动态解说条：选中变化时，下方「差异」卡实时改写文案，用一句话讲清「多付出什么、换回什么」。
  • 不可行档位：整列降透明度 + 行内「不可用」角标，不隐藏——保留对比意义。

数据来源

store.generateDrafts() 已返回三份 ProgramPlan，params.targets / proteinPerKg / trainingDays / mealsCount 全部现成。月度预期可由 kcalDelta × 30 ÷ 7700 在引擎侧补一个推导值。

11 · 决策期 · 加餐

档位的科学依据

三张研究曲线说清「为什么保守 3 练、均衡 4 练、进取 5 练」——选档不再是凭感觉。

为什么需要这页

01–03 给的是「对比」，但没回答「为什么」。用户最反感的不是选项多，而是不知道每个选项意味着什么。运动医学与睡眠科学已有充分研究：训练频次、睡眠时长、睡眠规律性是肌肉与力量增长的核心调控变量。把这些曲线作为档位差异化的可视化背书，让选择变成有根有据。

关键交互

  • 三曲线 Tab 切换：训练频次 / 睡眠时长 / 社交时差——每屏一张图，深度高于宽度，避免三张小图挤一屏。
  • 三档位标注到曲线：每个档位的关键参数（练几天 / 睡几小时 / 容忍多少时差）作为标记点叠在曲线上，让「选 4 练」直接对应曲线的力量最佳区。
  • 用户自身位置：基于 profile + preferred_time_slots 实时计算用户的「时差位置」，叠在曲线上做自我对比。
  • 底部科学结论：每张图配一句研究级结论，档位的差异不再是凭直觉。

数据来源

曲线是研究综述的标准化图示，不直接落库；档位标注是 TIER_SPECS 现有配置；用户位置由 profile + preferredTimeSlots 实时计算。

02 · 决策期

4 周强度预览

在承诺之前先看见代价——把抽象的「进取档」翻译成 28 个格子的具体生活。

现状痛点

用户在 setup 阶段对方案的认知只有 4 个数字，点「启用」等于盲签一份 4 周合同。这是后续执行率低、中途归档的根源——不是毅力问题，是预期没对齐。

关键交互

  • 7×4 网格：一行一周、一列一天，训练日填课程名首字、休息日留白，一眼看出「节奏」而非「总量」。
  • 色深即负荷：按 courseDurationMin 分三档深浅，第 3 周的强化周会明显变深，形成视觉上的「爬坡」。
  • 每周时长合计：右侧列分钟数，让「这周要投入 3 小时」成为可评估的数字。
  • 切换档位即时重画：与 01 共用分段控件，左右两个视图互为补充——一个看数字，一个看生活。

数据来源

ProgramDay.courseName / courseDurationMin / rest / dayIndex 已在 blob.days 中完整存在，草稿阶段即可渲染，无需落库。

03 · 决策期

内联约束向导

「去补全个人信息」是一个跳出链接，应该是一个当场就能改的表单。

现状痛点

现在 setup 阶段第一段是「1. 在『我 › 个人约束』填写…」，用户要点进二级页、找设置项、改完再回来重新生成。跨页跳转 + 上下文丢失是这一步最大的流失点，而这些约束本来就是方案的输入参数，理应长在方案页上。

关键交互

  • chips 化输入：训练天数给 3/4/5/6 快捷胶囊，器械与忌口多选 chips，比下拉框快一个数量级。
  • 实时结果预览：底部常驻一行「按此条件 → 4 练 · 健身房 · 每日 4 餐」的即时反馈，改动立刻可见。
  • 与 profile 双向同步：改动直接写回 profile 的 trainingDaysPerWeek / equipment / dietRestrictions / preferredTimeSlots，不引入第二套存储。
  • 不可行即时提示：条件冲突（如「每周 6 练」+「仅徒手」）当场给出黄色提示，而不是等生成后才知道。

数据来源

nutritionService.updateProfile 已支持这五列（迁移 0008 已加）。pickWeekTemplate(equipment, days) 已能按器械与天数选模板，预览文案可直接复用其返回。

04 · 执行期

今日驾驶舱

方案页每天被打开的理由只有一个：「我今天还差什么」——把它做成首屏。

现状痛点

现在生效态首屏是「目标 + 日期区间 + BMR/TDEE」，这是方案的参数，不是用户的进度。而真正该在首屏的「今天练什么、吃了几餐、还差多少蛋白」，被压在第二张卡的列表里，且没有进度感。

关键交互

  • 三环复用语义：红=摄入、绿=运动、青=营养均衡，与主页面三环完全一致，不新造隐喻。
  • 三条执行进度条：训练（未完成/已完成）、餐次记录（2/4）、蛋白（88/124g）——把「方案日程」翻译成三个可清空的待办。
  • 下一动作卡：只显示当前最该做的一件事（今日训练 / 下一餐），带直达按钮，不做信息陈列。
  • 天序计数：第 12 天 / 28，给长周期一个「已走过」的实感。

数据来源

三环复用 nutritionStore.summary；餐次记录来自 dietStore.meals 按 mealType 去重计数；训练完成态查 todoService.listTodos(date) 中 programId 且 category='workout' 的项——全部现成。

05 · 执行期

28 天周期地图

方案是 4 周的旅程，但界面只给了「本周 7 行」——把整段旅程铺开。

现状痛点

weekRows 只取 days.filter(d => d.date >= today).slice(0, 7)，用户永远只能看到未来 7 天。已经走过的日子在界面上完全消失——没有「我已经坚持了 12 天」的正反馈，这是长周期产品最致命的缺失。

关键交互

  • 全周期 7×N 网格：4 周就是 4 行，一眼看完整段旅程的长度和形状。
  • 状态色分五态：已完成（绿实心）/ 今天（蓝描边 + 呼吸点）/ 未来（虚线框）/ 已错过（红）/ 休息日（灰）——过去的每一天都有交代。
  • 阶段分组标注：适应期 / 强化期 / 冲刺期，让「为什么这周变累」有解释。
  • 点格子即聚焦：与现有 focusedDay 打通，点击后下方菜单区切到那一天（未来日可预览、过去日可回看）。

数据来源

格子状态 = blob.days 与 todoService.listAllTodos() 中 programId 匹配项的 status 做左连接——programReport.ts 里已有这段逻辑，抽成工具函数即可复用。

06 · 执行期

营养结构罗盘

菜单现在是纯文本列表，看不到「结构」——而饮食方案的核心恰恰是结构。

现状痛点

现在每餐只给「约 520 大卡 · 蛋白 42g」两个数字，用户无法判断这天的饮食是否均衡。而 ProgramMeal 里 protein / carb / fat 三个字段都已算好，却从未被可视化过。

关键交互

  • 三色堆叠环：蛋白 / 碳水 / 脂肪的供能占比，颜色沿用 --c-protein/--c-carb/--c-fat，与营养页同源。
  • 按餐次堆叠条：四餐各一条，宽度即热量占比，让用户看到「加餐是不是吃太多了」。
  • 目标对照刻度：环下方一条目标区间标尺，实际值落在区间内显示绿点、越界显示橙点。
  • 左右滑动切日期：与 05 的周期地图联动，滑动即切换聚焦日，保持同一份 focusedDay 状态。

数据来源

ProgramMeal.protein/carb/fat/kcal 由 programEngine 装配模板时算好；AI 菜单路径由 recipeGen 用食物库实算后写入 program_meals，字段一致，两条路径都能渲染。

参数演进图

调整历史现在是纯文本流水，看不出「方案被改成了什么样」的趋势。

现状痛点

现在每次调整渲染成「v3 热量缺口：-400 → -550」这样的文本行。三次调整之后就是一堵文字墙，用户看不出自己是在逐步加码还是反复摇摆——而这恰恰是判断方案健康度最重要的信号。

关键交互

  • 双线叠加：热量偏移用连续折线、训练天数用阶梯线，两种量纲共享时间轴，看清「是不是靠加训练硬扛」。
  • 节点区分来源：实心点=AI 复盘、空心点=手动，一眼看出哪些改动是你自己拍的、哪些是数据驱动的。
  • 点节点看 diff：点击弹出该次变更的 before → after，保留现有文本细节但不占常驻空间。
  • 摇摆检测提示：同一参数在 3 次内来回变动超过阈值时，给出「你在反复调整，建议先稳定一周」的温和提示。

数据来源

ProgramAdjustment[]（adjustmentsJson）已含 version / at / summary / changes[] / source，ProgramChange.before/after 是字符串，图上解析为数值即可，无需改结构。

08 · 执行期

体重航道图

减脂/增肌唯一的真相指标是体重曲线，但它现在只以「提醒卡」的形式闪现在主页。

现状痛点

utils/weightTrend.ts 已经能按目标分带判定（掉秤过快 / 反向增重 / 停滞），但产出只用在主页一张「可忽略的提醒卡」。判定逻辑有了，可视化没有——用户看到「掉秤过快」却不知道自己偏离了多少、该往哪拉回来。

关键交互

  • 目标走廊：不是一条目标线，而是一条半透明带（每周 ±0.3kg 的合理波动区间），落在带内即健康——这比单点目标更符合真实生理。
  • 偏离点标色：带内绿点、带外橙点，连续 2 次带外才升级为红色告警，避免单日水分波动造成误报。
  • 判定文案复用：图表下方直接渲染 weightTrend 的结论文本，逻辑不重写。
  • 与方案联动：走廊宽度按方案档位计算（进取档走廊更陡），图上的带就是「这个方案本来预期的轨迹」。

09 · 复盘期

复盘卡片流 · 单条采纳

现在的复盘是「全盘接受或全部放弃」——把颗粒度拆到单条，采纳率会完全不同。

现状痛点

AI 复盘给出 diagnosis + advice[] + changes[]，但 UI 只提供一个「采纳建议」按钮，一次性应用整个 patch。如果三条建议里有两条认同、一条不接受，用户只能全部放弃——这是设计在逼用户做二选一。

关键交互

  • 建议卡片化：每条建议独立成卡，带自己的开关，勾选状态实时反映在下方的汇总 diff 上。
  • 汇总实时计算：勾选变化时，底部「将变更为」区域即时重算——用户能试算「只采纳前两条会怎样」。
  • 数据先行：诊断之前先放本周 vs 上周的三条对比条，让用户自己先有判断，再看 AI 怎么说（避免盲目信任）。
  • 仍然走钳制：无论勾选几条，最终仍经 clampAdjustment——越界值在卡片上直接标注「已钳制」。

数据来源

reviewProgram() 已返回结构化 changes[]；增量采纳只需把勾选子集重新喂给 clampAdjustment，store.adjust 与后端契约完全不变。

10 · 归档期

结营成绩单

坚持 28 天是一件值得被庆祝的事，现在它只是一个弹层和一行历史列表。

现状痛点

归档后方案变成历史列表里的一行「减脂 · 均衡 · v5」，点开是一个中等高度的弹层，四个统计格加一行小字。没有对比、没有闭环、没有下一步——用户拿不到「我到底改变了什么」的答案，也就没有动力开启下一期。

关键交互

  • 开始 vs 结束对照：体重、摄入、训练频率三项并排对比，这是唯一能回答「有没有用」的形式。
  • 完成度大数字：ProgramReport 的 schedule.done/planned 直接换算，诚实呈现（82% 比「已完成」更可信）。
  • 成就徽章：按数据规则颁发（全勤 / 首次连续打卡 / 蛋白达标率高），纯前端判定，不引入新表。
  • 下一步 CTA：底部直接给「开启下一期」按钮，把归档从终点变成中转站。
